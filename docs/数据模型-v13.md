# 数据模型 · v13（任务 2：外部权威编号 + 关系三元组）

执行窗口：提交冻结期（SPEC-v13 任务 2）。借鉴 opensupplyhub / supplychaindata.exchange（SC-DEX）
的**结构**——实体用外部权威编号做可选标识、关系用三元组单表承载；**只借结构，不套用其
schema/ID 词汇表，不引入其数据**。本轮只做数据层与导入链路，不改任何引擎数值口径
（固定演示案例数值逐位不变，已由 tests/test_v13_solver.py 与 Windows E2E 双重复核）。

## 一、版本与变更总览

- `SCHEMA_VERSION`：**4 → 5**（pilot/db.py）。
- 变更内容（纯增量，不改动既有列/数据）：
  1. `supplies` 表新增可选列 `external_id TEXT NOT NULL DEFAULT ''`（供给批次的外部权威编号）；
  2. `batches` 表新增可选列 `external_id TEXT NOT NULL DEFAULT ''`（全局批次实体的外部权威编号）；
  3. 新增 `relations` 表：`id / from_id / to_id / rel_type / created_at`，
     `UNIQUE (from_id, to_id, rel_type)` 保证三元组幂等；
  4. `Database` 新增 `add_relation(from_id, to_id, rel_type)`（幂等写入）与
     `list_relations(from_id=None, rel_type=None)`（过滤读取）；
  5. v13 修正：`meta.schema_version` 在迁移成功后盖章为当前版本（此前 `INSERT OR IGNORE`
     会让老库版本号永远停在创建时的值，靠幂等迁移重跑掩盖；盖章后版本号恢复真实语义，
     也让回滚演练可验证）。
- 写入链路：`pilot/server.py` 单行录入 / CSV 整批导入两条路径均把 `supply.external_id`
  持久化到 `supplies.external_id` 与 `batches.external_id`（含 upsert 冲突分支）。

## 二、ER 概览（v5）

```
users 1─* sessions
users 1─* tasks 1─* supplies（task_id, supply_id, batch_id, supply_json, external_id）
                    │
                    └─* batches（batch_id 全局唯一, supply_json, original_mass_t, external_id）
                            │
tasks 1─* runs 1─* selections            └─* reservations（全局批次库存）
tasks 1─* evidence_tasks 1─* evidence_versions
tasks 1─* feedback
relations（from_id, to_id, rel_type）—— 实体间关系三元组，单表承载，全局唯一
audit_log（actor, event, entity, before/after）
meta（schema_version 等）
```

关系三元组约定（建议词汇，允许按需扩展，不做 CHECK 强约束，词汇表治理归本文档）：

| rel_type | 含义 | from → to |
|---|---|---|
| `supplies` | 供应关系 | 供应商实体编号 → 批次编号 |
| `substitutes` | 替代/可替换关系 | 批次/物料编号 → 批次/物料编号 |
| `same_as` | 同一实体的外部编号映射 | 内部编号 → 外部权威编号 |

## 三、external_id 约定

- **定位**：可选（OPTIONAL）标识，绝替代内部主键（`supply_id` / `batch_id` 仍是引擎与
  库存的唯一事实键）；选项身份 option_id、库存核算、N-1 聚合全部不读该列。
- **推荐取值**：供应商实体用统一社会信用代码（18 位）；批次用上游系统权威批次编码。
- **取值纪律**：非空即视为「已对齐外部系统」，写入方负责其真实性（不伪造——红线 1）；
  引擎与报告层不因该列存在而改变任何数值。
- CSV：`external_id` 为**可选列**——旧文件（无该列）导入行为与 v12 逐字段一致；
  新文件带该列时透传（`src/material.py load_supplies_csv` → `pilot/api.py SUPPLY_FIELDS`）。

## 四、迁移说明（v4 → v5）

- 方式：`_migrate` 幂等迁移——`SCHEMA_SQL` 全部 `CREATE TABLE IF NOT EXISTS`；
  老库 `supplies`/`batches` 缺 `external_id` 列时 `ALTER TABLE ADD COLUMN ... DEFAULT ''`；
  `relations` 表与唯一索引由 CREATE IF NOT EXISTS 兜底；每步校验列存在性，可重复执行。
- 兼容：v4 及更早库打开即自动升级；既有数据逐行逐字节保留（测试断言 `supply_json`
  原串相等）；新列缺省空串，不污染任何既有读取。
- 可回滚演练：升级前 `backup_to`（或文件级 copy）→ 升级 → `restore_from` 恢复回 v4 →
  再打开自动重新升级。恢复语义沿用 P0-4（WAL checkpoint + 文件锁重试）。
- 迁移证据：`tests/test_v13_datamodel.py` 七项——新库直建 / v4 升级保数据 / 重复迁移
  幂等 / 回滚演练 / 旧 CSV 兼容 / 新 CSV 透传 / payload 往返稳定。

## 五、明确不做的事

- 不为 relations 开 HTTP 端点（数据层先行，接口随真实数据接入设计，避免空转面）；
- 不把 external_id 引入 option_id / 护照哈希 / 因子解析（标识与核算彻底分离）；
- 不改动已提交材料与任何演示数值。
