# ADR-0005：撮合建议即算即返，不落库

状态：已接受（v16 实现既成事实；v17 任务 5 升格为决策记录）。

## 背景

v16 把多需求-多批次撮合引擎（src/matching.py，Gale-Shapley 容量变体）接上试点
工作台时，面临一个语义分叉：撮合结果要不要像「方案确认→confirmed 预留」那样
写进数据库（产生跨任务的状态），还是作为只读试算即算即返？

关键约束：

- 库存真相只有一个：批次全局可用量 = 原始量 − 有效预留 − 已确认占用。撮合的
  「分配」若落库，就成了第二种事实来源——建议与预留混在一起，任何一方都可能
  被误读为对库存的占用；
- 交易语义不存在：撮合输出的「建议到厂成本」是演示毛利模型核算口径，不是报价；
  撮合建议不构成交易、不产生预留（页面三处明示）。把建议落库等于替用户隐式
  创建了从未被确认的意向状态；
- 法律与合规风险：自动生成的跨需求分配若持久化，可能被外部理解为平台对供需
  双方作出了某种安排/承诺；
- 试点阶段没有真实交易信号：任何落库设计（状态机、过期、通知）都缺乏真实
  使用反馈来验证，先建状态层是过早设计。

## 决策

- 撮合只提供只读试算：`POST /api/matching/preview`（v16）与
  `POST /api/matching/sheet` 建议单导出（v17）共用同一计算（`_matching_payload`），
  即算即返、**不写 runs、不建任何表**，仅写 audit 留痕（matching.preview /
  matching.sheet）供审计与复算对照；
- 建议单由前端 Blob 下载，文件是否存档由用户决定，服务端不保存副本；
- 页面与建议单恒定标注：「撮合建议（非交易/非预留）：即算即返、不落库，
  不产生预留或占用，不改变批次库存真相」；批次容量一律按实时全局可用量现算，
  不缓存不快照。

## 后果

- 正面：库存真相单一（预留/占用是唯一事实）；无隐式意向状态；审计可对照
  （同入参重算逐位一致，tests/test_v17_matching_sheet.py 数值同源断言把守）；
  服务端无状态清理负担；
- 负面：撮合结果不跨会话留存——用户关页即逝（重算可复现，代价是一次秒级计算）；
  无法基于历史建议做跟踪分析（audit 记录了入参与汇总计数，可部分弥补）。

## 升级为落库的触发条件（出现任一才重开本决策）

1. **真实客户信号**：试点客户明确要求「保存某次撮合方案并跟踪后续」；
2. **交易层需求出现**：双方在平台内达成意向、需要从建议生成预留/订单时——
   届时新建议状态机（draft→accepted→expired 等）与交易/预留层的边界必须
   一并设计，建议状态永不直接占用库存；
3. 多组织撮合（超出单组织部署范围）出现事实上的平台居间语义时。

触发前，任何「顺手把建议存起来」的实现都视为对本决策的违反。
