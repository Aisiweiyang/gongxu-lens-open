# ADR-0006：大案例异步作业为进程内存态

状态：已接受（v19；v18 实现既成事实的决策补记）。

## 背景

v18 任务 3 引入大案例后台计算（`POST /runs?async=1` + 作业轮询）。作业状态放在哪里
存在分叉：入 SQLite（像 runs/selections 那样成为事实数据）还是进程内存。

关键考量：

- 作业不是业务事实：它是「一次计算的进度指针」，计算完成后的权威产物是
  runs 表里的运行快照（含输入快照与结果），作业本身没有留存价值；
- SQLite 单写架构：作业状态的高频更新（queued→running→done）与业务写入共享
  单写锁，为进度指针引入写竞争不值得；
- 部署口径为单组织局域网单进程（商用试点手册 §7），不存在多进程共享作业表
  的需求；引入跨进程作业存储（Redis/DB 轮询）属过早设计。

## 决策

- 作业表为**进程内存字典**（`_ASYNC_JOBS` + 单作业守卫槽），不落库；
- 服务重启即丢失全部作业——前端与 API note **如实告知**「需重新提交」，不伪装
  为持久任务；
- 已结束作业按保留上限（200）清理最旧记录，防内存无界；
- 作业的最终产物（run 快照）照常落 runs 表——丢作业 ≠ 丢已完成的计算结果。

## 后果

- 正面：零 schema 变更、零写竞争、实现与测试简单（tests/test_v18_async_runs.py）；
  与 ADR-0005 同一精神——非事实数据不持久化；
- 负面：重启后进行中的大案例（十几分钟级）作废重算；无法跨进程/多机扩展
  （当前部署口径不需要）。

## 升级为持久作业队列的触发条件（出现任一才重开本决策）

1. 真实试点出现「服务重启导致大案例重算」的实际客诉/损失信号；
2. 部署形态升级为多进程/多机（届时需共享作业存储与分布式锁，重新设计守卫语义）；
3. 出现更高频的大案例提交（单作业守卫排队成为瓶颈）。

触发前，「顺手把作业写进数据库」视为对本决策的违反。
