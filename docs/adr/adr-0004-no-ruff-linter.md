# ADR-0004：不引入 ruff 静态检查（评估结论）

状态：已接受（v16 任务 5 评估；默认不引入，未来条件变化可重开）。

## 背景

SPEC-v16 第四节预核验：ruff（MIT OR Apache-2.0）与 ruff-pre-commit 仓库可达、
双许可确认（2026-09-10 实检）。借「静态检查应进提交流程」的实践做一次引入评估
（SPEC 任务 5：只评估，默认不引入）。

## 评估

支持引入的理由： Picks of speed、单二进制、规则全默认可增量；能在提交前拦
未用变量/明显笔误。

反对引入的理由（当前占优）：

1. **全仓风格 churn**：仓库约 3 万行既有代码按既有风格写就；一次接入必然产生
   大面积与业务无关的格式改动，污染 git blame 与逐位核验基准（红线 3 的工作面），
   与「移动文件须同步全部引用」同级别的无谓 churn——v15 已因白名单漏加翻车一次，
   不应再主动制造全仓 diff。
2. **零依赖文化**：运行时零第三方依赖是本项目的对外声明（红线 4/7）；开发期
   依赖虽不违背字面，但会稀释该口径，且需要维护 pre-commit 钩子在 WSL/Windows
   双环境的行为一致。
3. **既有看护已密**：240 项测试 + 1 个演示案例 + 6 组随机独立穷举 + 文案门禁（test_docs_wording）
   + E2E console 零错误断言 + verify_release 哈希核验，已经覆盖 ruff 大部分
   高价值检出面的下游后果。

## 决策

不引入 ruff（本轮）。若未来满足以下任一条件可重开：多人协作成为常态；
代码量或贡献频率显著增长导致 review 负担可感；或发生一次可归因于低级静态
缺陷的线上问题。
