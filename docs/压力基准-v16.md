# 服务器压力基准 · v16（SPEC-v16 任务 2）

执行时间：2026-09-11。被测对象：试点服务器（`pilot/start_pilot.py`，stdlib
http.server + SQLite WAL）。目的：v12 交接遗留项——容量声明「<20 并发」
（docs/商用试点手册-v10.md 第 7 节）从未实测，试点前给客户真实数字。

## 一、方法

- 脚本：`benchmarks/load_benchmark.py`（零依赖：stdlib threading + http.client）。
  方法学借鉴 Locust（MIT，SPEC-v16 第四节核验记录）的「虚拟用户 × 固定行为序列 ×
  并发爬坡 + P50/P95/P99 + 错误率」思想——**仅借方法学，未引入 locust/gevent
  依赖**（红线 4/7）。
- 行为序列（每虚拟用户每轮固定六步，对应真实操作路径）：
  ① 会话校验 `GET /api/auth/me` → ② 任务列表 `GET /api/tasks` →
  ③ 运行引擎（小案例：2 供给 15t，穷举路径）`POST /api/tasks/{id}/runs` →
  ④ 结果读取 `GET /api/runs/{id}` → ⑤ 护照下载 `GET /api/tasks/{id}/passport`。
- 并发爬坡档位：1 / 5 / 10 / 20 / 30；每虚拟用户每档 3 轮。
- 隔离与公平性：每一档使用**全新服务器子进程 + 空库**（临时目录，避免跨档状态
  污染：运行快照累积、进程级缓存、登录限流窗口残留）；压测客户端与服务器为
  独立进程（不共享 GIL）；每档计时前 1 次不计入统计的预热（因子表加载 + 缓存建立）。
- 两种登录口径（分列，不混写）：
  - **shared**（业务容量口径）：全体虚拟用户共享一个编辑会话，测业务路径容量；
  - **per-user**（限流口径）：每虚拟用户序列内各自登录——服务器「同 IP 900 秒
    最多 10 次登录尝试」防暴力破解限流，单机压测（所有连接同源 127.0.0.1）
    下 >10 并发登录必现 429，如实呈现。
- 百分位：最近秩法（nearest-rank），确定性；每步延迟覆盖从请求发送到响应体读完
  （护照等大响应体如实计入）。
- 本脚本只产生测量数据，不下「达标」结论；对照声明见第三节。

## 三、结论：实测容量与「<20 并发」声明对照

1. **「预计 <20 并发操作」声明成立，且有裕量**：20 并发（shared 口径）两平台
   全链路零错误，引擎运行 P95 = 0.76s（WSL）/ 1.80s（Windows），其余读路径
   P95 ≤ 0.9s（WSL）/ 0.92s（Windows，passport 步 0.59s@P95 除外，见原始表）。
2. **30 并发仍零错误，但体验开始退化**：引擎 P95 升至 1.28s（WSL）/ 1.19s
   （Windows），P99 约 1.3–2.1s；吞吐不升反平（约 75–87 req/s，单机 CPU 饱和）。
   本版本适用边界仍应在 **≤20 并发**，与声明一致。
3. **登录限流是真实部署约束（非缺陷）**：局域网各终端独立 IP 时不触发；若经
   NAT/代理共用出口 IP，>10 并发同时登录会出现 429——需错峰登录或分批上线。
   该限流是防暴力破解设计（v12 既有安全项），本次实测验证其按设计工作。
4. **Windows 引擎慢于 WSL（既有已知项）**：10–30 并发档引擎 P50 约 0.5s（WSL）
   vs 1.0–1.5s（Windows），约 2–3 倍，与 v12 交接记录的「Windows 解释器显著慢」
   一致；未改产品代码迁就（红线）。
5. **SQLite WAL 单写未见写锁竞争**：各档含写入步骤（run 落库、audit）全程
   零 500/零超时，小团队并发规模下 WAL 串行写不构成瓶颈。

### 部署建议（更新手册口径的依据）

- 单组织/单园区局域网部署，**容量口径定为：≤20 并发操作，峰值引擎等待约 2 秒；
  30 并发可用但响应明显变慢**。超过 20 并发或多组织共用，需另行评估（本版本范围外）。
- 经 NAT/代理共用出口 IP 的现场：向客户说明登录限流语义（同 IP 900 秒内 10 次），
  培训时安排错峰登录；勿为压测数字调宽该安全参数。
- 试点硬件按本次测试机规格或更低一档（本次为 24 逻辑核台式机）即可满足 ≤20 并发。

## 四、边界与限制（如实）

- **小案例口径**：行为序列的引擎步用 2 供给 15t 小案例（穷举路径）。大案例
  （30 供给完整前沿单次 19.2s，见 benchmarks/求解基准-v14.md）在并发下的表现
  未覆盖——试点如跑大案例，应预期为「单次秒级到十秒级 + 并发排队」，容量结论
  不外推。
- **采样量小**：每档 3 轮 × 最多 30 用户，单步样本 15–450 条；毫秒级 P50/P95
  不具统计显著性，结论以数量级、错误率与趋势为准。
- **回环网络**：客户端与服务器同机 127.0.0.1，无真实局域网网络抖动；真实部署
  延迟应加上局域网 RTT（通常 <1ms，可忽略）。
- **空库起点**：每档全新空库；万行级历史数据下的表现由「SQLite 万行内无风险」
  既有结论与运行快照按 task_id 索引支撑，未单独压测。
- 压测全部发生在临时目录空库，未触及仓库真实数据与任何已提交材料。

## 五、增补（v17 任务 3）：大案例（30 供给）单发与低中并发实测

> 2026-09-12 至 09-14 执行。补第四节「小案例口径」边界：大案例（30 供给、需求 20t、
> 触 FRONTIER_CAP 截断，与 benchmarks/求解基准-v14.md 30 批次行同源）经试点服务器
> HTTP 全路径的单发与 1/2/4 并发实测。**本节只追加，不改动上文 v16 任何实测数字。**

### 方法

- 脚本：`benchmarks/load_benchmark.py --fixture large --levels 1,2,4 --iterations 1
  --login shared --tag v17large-wsl`（WSL，Python 3.14.4，24 逻辑核）。
- 夹具：large=30 供给、需求 20t，与 `make_case(30)` 同 rng 种子（1030）同参数取值
  顺序，30 批次的容量/熔指/价格/含运/产率/距离**逐位一致（实检比对 0 mismatch）**；
  两处差异如实标注：① factor_id 用服务器演示因子表的 DEFRA-ARTIC-HGV-DIESEL-2024
  （服务器环境无 make_case 的 TEST-TRANSPORT-2025，保证运输碳可算、与真实请求路径
  一致）；② API payload 必填的 material_name_raw/origin 取演示值。
- 每档全新服务器子进程 + 空库 + 1 次不计入统计的预热运行；每虚拟用户 1 轮序列；
  客户端超时放宽至 1800s（large 档，small 档仍 300s）。
- 引擎步 = `POST /api/tasks/{id}/runs` 完整分析（前沿 + 敏感性 + N-1 + 区间等全流程），
  非单纯前沿求解——这是与求解基准-v14（单段 19.2s）数字不可直接对比的原因。

### 实测（shared 口径；原始数据逐字存于 benchmarks/压力基准-raw-v17large-wsl-shared.{json,md}）

| 并发 | 引擎步 n | 错误 | 引擎步 P50/P95 ms | 单次等待折算 | 结果读取 P95 ms | 护照 P95 ms | 墙钟 s |
|---|---|---|---|---|---|---|---|
| 1 | 1 | 0 | 809,011.8 / 809,011.8 | **≈13.5 分钟** | 622.4 | 441.6 | 810.6 |
| 2 | 2 | 0 | 1,183,928.7 / 1,191,699.5 | ≈19.7–19.9 分钟 | 1,643.5 | 537.2 | 1,193.6 |
| 4 | 4 | 0 | 1,086,322.2 / 1,092,179.8 | ≈18.1–18.2 分钟 | 973.9 | 964.2 | 1,093.1 |

- 全档全步骤（me/tasks/run/result/passport）错误数为零；大案例运行结果体量约
  22.6 MB（临时库 runs.result_json 实测），结果读取与护照下载均在亚秒到 1.6s。
- 执行横跨机器休眠：每步延迟取自 `time.perf_counter`（Linux CLOCK_MONOTONIC，
  休眠不计时），墙钟数字为各自档内 awake 口径；原始 JSON 的 generated_at 供核对。

### 结论：试点跑大案例的预期等待（量级结论，样本极小不作统计断言）

1. **单发等待约 13–14 分钟**（实测 809s）；**2–4 并发下单次等待约 18–20 分钟**且
   全链路零错误——并发没有线性恶化单次等待（引擎的 CP-SAT 重段释放 GIL、多核
   可吸收），2 并发与 4 并发的单次等待相当（样本 n=2/n=4，仅量级结论）。
2. **为什么不是求解基准的 19.2s**：完整分析 = 前沿求解 1 次 + 敏感性每个 OAT 场景
   各重枚举一次方案集 + 翻转阈值/联合情景 + N-1 压测，全部随供给数放大；19.2s
   只是其中前沿单段。此前完整分析耗时从未实测，本节为首个端到端数字。
3. **试点建议口径**：大案例（≈30 供给）应作为「单发后台任务」使用——提交后预期
   十几分钟等待，期间页面不可做其他操作（同步请求）；避免多名用户同时提交大案例
   （虽零错误，但 CPU 饱和、等待拉长）；小案例（日常十几批次内）秒级体验不受影响。
   同步请求语义下浏览器/代理超时是真实风险（本测客户端超时放宽至 30 分钟）——
   异步运行路径为后续版本候选（ADR 待立）。
4. **Windows 部署会更慢**：既有口径 Windows 解释器慢于 WSL 约 2–3 倍（v16 小案例
   实测）；大案例未在 Windows 实测（本轮 WSL 一轮口径），预期等待应按更慢一档
   估计，如实向客户说明。
5. 边界：样本 n=1/2/4 不具统计显著性；回环网络；空库起点；预热不计入；因子/运价
   为演示配置（非真实项目数据）。容量结论（≤20 并发）仍是小案例口径，不因本节
   外推到大案例并发。

## 六、增补（v22 任务 3）：并行化后大案例端到端单发实测

> 本节以完全相同的方法学复测并行化后的单发，替换 v19 的「推算 550–560s」。
> **本节只追加，不改动上文任何实测数字。**

### 方法

- 与第五节完全同口径：`benchmarks/load_benchmark.py --fixture large --levels 1
  --iterations 1 --login shared --tag v22parallel-wsl`（WSL，Python 3.14.4，
  24 逻辑核；large 夹具与第五节同源：30 供给、需求 20t）。
- 每档全新服务器子进程 + 空库 + 1 次不计入统计的预热运行；引擎步 = `POST
  /api/tasks/{id}/runs` 完整分析全流程；每步延迟取自 `time.perf_counter`
  （休眠不计时；本轮一次性连续完成，无休眠事件，墙钟与 CPU 时间交叉核对一致）。

### 实测（shared 口径；原始数据逐字存于 benchmarks/压力基准-raw-v22parallel-wsl-shared.{json,md}）

| 并发 | 引擎步 n | 错误 | 引擎步 P50/P95 ms | 单次等待折算 | 结果读取 P95 ms | 护照 P95 ms | 墙钟 s |
|---|---|---|---|---|---|---|---|
| 1 | 1 | 0 | 549,220.7 / 549,220.7 | **≈9.2 分钟** | 394.4 | 256.6 | 550.17 |

- 全步骤（me/tasks/run/result/passport）错误数为零；档计量墙钟 550.17s 之外，

### 结论：并行化的端到端收益（与第五节串行口径对照）

1. **单发引擎步 809.0s → 549.2s（≈1.47×；样本各 n=1，仅量级结论）**：v19 推算
   550–560s 与实测相符，推算值就此替换为实测。端到端收益（1.47×）低于引擎层
   analyze_task 的 2.4×（430.8s → 179.3s，见 docs/完整分析耗时结构-v18.md 增补
   节）属预期——完整分析中前沿求解段占比小（v18 拆解约 5%）并行收益有限，且
   HTTP 全路径的夹具/序列化/落库/传输等固定串行部分不随并行化缩短。
2. **试点预期等待更新：30 供给大案例单发约 9–10 分钟**（此前串行口径 13–14
   分钟）；2–4 并发未复测（并行化后的并发表现未测，如实标注）。大案例推荐
   走后台异步路径（供给 ≥16 自动启用，ADR-0006）。
3. 边界沿用第五节：样本 n=1 不具统计显著性；回环网络；空库起点；预热不计入；
   因子/运价为演示配置。容量结论（≤20 并发）仍为小案例口径，不因本节外推。
