## 二、发现清单

### 高

**F-01 【高】「恢复最近备份」按钮实际恢复的是最旧的备份**
- 位置：`pilot/static/app.js:850`（`var last = res.backups[0]`）+ `pilot/server.py:822`（`sorted(..., key=lambda b: b["name"])` 升序）。
- 反例或推理：服务端按名称升序排列，备份文件名含时间戳 → `[0]` 是最早的备份；点「恢复最近备份（危险）」会把数据库回滚到最老状态，破坏性数据丢失且与按钮文案相反。
- 建议：服务端 `_api_list_backups` 按名称降序（或显式返回排序方向字段），前端取「名称最大」项；并加一次「将恢复到 <时间戳> 的备份」确认文案。

**F-02 【高】API 路径可注入 NaN/Infinity：容量预留冲突检测被永久击穿**
- 位置：`pilot/server.py:84-93`（`_read_body` 用 `json.loads`，Python 默认接受 `NaN`/`Infinity`）+ `pilot/server.py:726-759`（`_api_reserve` 的 `float(body.get("quantity_t") or 0)`）+ `pilot/api.py:37-43`（`_to_float` 接受 `float("nan")`）。
- 反例或推理（已实测）：`json.loads('{"quantity_t": NaN}')` 成功；`float("nan") <= 0` 为 False → 穿过正数校验；`reserved + NaN > available` 恒 False → NaN 写入 reservations。之后 `SUM(quantity_t)` 恒为 NaN，该供给的所有后续预留冲突检测全部失效（任何数量都放行）。此外 `_to_float` 让向导/单条录入的 NaN 供给进入引擎：NaN 供量与需求的比较恒 False → 数量门槛误判「≥需求」→ 单供资格通过 → NaN 成本方案进入 Pareto（NaN 既不支配也不被支配，`min(key=total_cost)` 可能选出 NaN 方案为「最低成本」）；`serialize_result` 的 `json.dumps` 还会输出非法 JSON `NaN`，浏览器 `JSON.parse` 直接失败。
- 建议：`_read_body` 用 `json.loads(raw, parse_constant=lambda c: (_ for _ in ()).throw(ValueError(...)))` 拒绝 NaN/Infinity；`_to_float` 与 `_api_reserve` 增加 `math.isfinite` 校验（与 CSV 体检口径一致）。

**F-03 【高】重复 supply_id / demand_id 被静默丢行或覆盖，体检未报告（与 A08「拒绝静默丢行」冲突）**
- 位置：`src/imports.py:53-122`（preflight 无重复 ID 检测）+ `src/material.py:138-139, 204-205`（`seen` 集合命中即 `continue`，注释声称「结构错误已在体检中报告」，实际未报告）+ `pilot/server.py:505-515`（导入 `INSERT OR REPLACE`，同一 CSV 内同 ID 不同内容 → 最后一行静默胜出）。
- 反例或推理（已实测）：CSV 两行同 `supply_id=X1`（内容不同）+ 一行 X2，`strict=True` 加载成功、`issues=0`、结果只剩 `[X1, X2]`——一个真实批次在零提示下从分析中消失，直接改变成本/韧性结论。试点导入路径同理（同 CSV 同 ID 覆盖、无警告）。
- 建议：preflight 增加「ID 重复（含行号对）」structure 级 issue（内容相同判定为重复、内容不同判定为冲突）；strict 拒绝；pilot 导入预览把同 ID 多行列为问题并要求显式改名；单行幂等覆盖保留（B02 同 ID 重复提交=覆盖是合法幂等，但要区分「单行提交」与「批内重复」）。

### 中

**F-04 【中】基准原生价缺失时，「较基准」成本差实际参照第一个单供方案**
- 位置：`src/material.py:816, 851`（`baseline_total_cny = options[0]["total_cost_cny"]`，未检查 options[0] 是否 baseline）。
- 反例或推理（已实测）：`baseline_virgin_price_cny_per_t=None`（真实数据常见缺报价）→ 无 baseline 选项 → options[0] 为第一个单供。实测：乙 cost_delta=-2842.5、全部组合 cost_delta 为负且被标「成本与碳双降」，但这些差值实为「vs 甲」而非「vs 基准」；报告/网站/护照均以「较基准」展示 → 误导决策。只有当首个单供恰好缺价时 delta 才碰巧为 None。

**F-06 【中】工作台 Pareto 悬停失效且折线遮挡圆点（F06/F07 修复未同步到 pilot 工作台）**

**F-08 【中】restore_from 失败路径使数据库连接永久关闭，服务全程 500 直至重启**
- 位置：`pilot/db.py:196-207`（`self.conn.close()` 之后无 try/finally 重开；`shutil.copyfile` 抛异常则连接保持关闭）。
- 反例或推理：meta 校验通过但 copy 阶段失败（磁盘满、备份文件被外部进程截断/替换、权限变化）→ 异常冒泡为 500，且 `self.conn` 已关闭、WAL sidecar 已删除——此后所有请求（含只读）全部 `ProgrammingError` → 500。管理操作失败不应瘫痪整个服务。
- 建议：`restore_from` 用 try/except 包裹 copy 阶段，失败时按原路径重开连接（或恢复被删 sidecar 前的状态）再抛错；增加一次失败注入测试。

**F-11 【中】证据来源类型关键词启发式把自报报告判为第三方最高级**
- 位置：`src/evidence_quality.py:46-52`（`_source_type`：文本含「报告/检测报告/认证/第三方」任一即判「第三方独立检测/认证报告」）。
- 反例或推理（已实测）：`evidence_source="供应商自检报告（内部实验室）"` → 来源类型=1、独立核验=1、总等级「高」。而 `SOURCE_TYPE_SCORES` 中「供应商自报+检测报告」=2 的档位因首分支命中而成为死代码。质量分虽不替代准入门槛，但「高」等级展示会误导使用者对证据强度的判断，与 A06「来源类型拆清、演示来源不自动获得最高评级」的精神相悖。

**F-12 【中】N-1 失效实体按 supplier_name 字符串聚合，缺少稳定供应商实体 ID**
